# APK Size Audit

## 1. Why the previous APK was ~60 MB

**Root cause identified: the release APK was a "fat"/universal APK.**

`.github/workflows/build-flutter-apk.yml` ran `flutter build apk --release`
with no ABI restriction. Flutter's Android build packages the Flutter/Dart
native runtime (`libflutter.so`, the AOT-compiled `libapp.so`) plus every
native `.so` library pulled in by plugins (audio_service/just_audio's
ExoPlayer-based media3 natives, sqflite) **once per target CPU
architecture** — by default `armeabi-v7a`, `arm64-v8a`, and `x86_64`. A
"universal" APK bundles all three copies side by side, even though any one
device only ever uses one. This is the single dominant contributor to APK
size for any real Flutter app, and this app's bundled data assets are far
too small to explain 60 MB on their own (see §3).

## 2. Fix applied

`flutter build apk --release --split-per-abi` now produces one APK per
architecture instead of a universal one:

- `app-arm64-v8a-release.apk` — every real Android phone sold since ~2018
  (the entire modern Android install base for a general-audience app).
- `app-armeabi-v7a-release.apk` — older 32-bit-only devices.
- `app-x86_64-release.apk` — emulators/Chromebooks; not published as a
  direct-download release asset since real end users won't need it.

CI now publishes `app-release.apk` (renamed from the arm64-v8a build,
covering the overwhelming majority of real devices) and
`app-release-armeabi-v7a.apk` (fallback) to the `latest-apk` GitHub Release,
alongside the AAB. **This has no effect on the Google Play distribution
path** — Play has always installed only the architecture a given device
needs from the AAB; the fat-APK problem only affected the direct-download
APK offered outside Play.

Expected impact: an arm64-v8a-only APK typically runs roughly a third to a
half the size of the equivalent universal build for a Flutter app of this
plugin footprint — this will be confirmed against the actual rebuilt
artifact sizes once CI completes (GitHub's artifact API reports exact
byte sizes even without downloading the file — see the size comparison
appended to this doc after the next green CI run).

## 3. Other size sources checked (not significant contributors)

- **Bundled Qur'an/Adhkar/font/icon assets**: `assets/quran` (3.0 MB, Qur'an
  text+translation+transliteration for all 6,236 verses), `assets/icon`
  (384 KB), `assets/fonts` (148 KB, AmiriQuran), `assets/images` (76 KB).
  Combined, under 4 MB uncompressed — and these compress further inside the
  APK's zip container. Not a meaningful factor next to a ~60 MB total.
- **Android resource shrinking**: `android/app/build.gradle.kts` already
  has `isMinifyEnabled = true` and `isShrinkResources = true` (R8 +
  resource shrinking both on), and `proguard-rules.pro` carries no
  overly-broad `-keep` rules that would defeat shrinking. No change needed
  here.
- **Launcher icons**: standard per-density mipmap/adaptive-icon PNGs
  generated by `flutter_launcher_icons`, each a few KB — not a factor.

## 4. What was not verifiable in this environment

This build sandbox's network policy blocks direct access to Azure Blob
Storage (`*.blob.core.windows.net`), which is where GitHub Actions serves
artifact *contents* from (only `raw.githubusercontent.com`-style GitHub
hosts are reachable here — the same constraint documented in `docs/15`
§2). This means the actual `app-release.apk` file could not be downloaded
and unzipped in this sandbox to produce a literal per-file byte breakdown
of its contents. The audit above is a structural analysis of the build
configuration and source assets rather than a `unzip -v` listing of the
compiled binary. The artifact **size metadata** (total bytes) is still
directly available via the GitHub Actions API without downloading the
file, and is used to confirm the fix's real-world impact below.

## 5. Tajweed alignment check — attempted, blocked by sandbox network policy

A follow-up to `docs/16` §"research findings": before enabling Tajweed
color-highlighting from the `cpfair/quran-tajweed` corpus, this session
attempted to verify that its character offsets still align with this app's
bundled Arabic text. That corpus's README pins its offsets to one specific
snapshot of the Tanzil Uthmani text (a file attached to a GitHub issue,
downloaded "ca. Apr 6, 2017"), rather than to the live `quran-tajweed`
repository tree. Fetching that specific attachment failed in this sandbox
(`github.com/cpfair/quran-tajweed/files/.../quran-uthmani.txt` returns a
proxy error here, since it isn't a normal repository file path and this
sandbox's GitHub access is scoped to repos explicitly added to the session).
Tajweed highlighting therefore remains unimplemented, unchanged from
`docs/16`'s conclusion — this is disclosed as an attempted-but-blocked check
rather than silently dropped.

## 6. Before / after — confirmed

Measured from commit `c40c082`'s CI run (GitHub release asset sizes, exact
bytes, no download/unzip required to read them):

| Build | Size | Change |
|---|---|---|
| Universal APK (commit `1a9696c`, before this fix) | 59.7 MB | — |
| **arm64-v8a APK (`app-release.apk`, the primary download)** | **21.4 MB** | **−64%** |
| armeabi-v7a APK (`app-release-armeabi-v7a.apk`, fallback) | 19.1 MB | −68% |
| AAB (`app-release.aab`, Play Store path — unaffected either way) | 56.3 MB | ~unchanged |

The primary direct-download APK went from 59.7 MB to 21.4 MB — confirming
the universal-APK packaging was indeed responsible for the large majority
of the previously reported size, exactly as predicted in §1-§2. This lands
within this doc's own "Good: 20–35 MB" band for an app of this feature
scope (Tasbeeh counter, full Adhkar library, full Qur'an text/translation/
transliteration, Qari audio playback, Madani Mushaf/Tahajjud reading
modes). The AAB size is expected to stay roughly where it was, since it has
always carried all architectures for Play's per-device delivery — that was
never the size problem.
